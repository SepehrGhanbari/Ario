# Safe Cognitive Memory Snapshot and Recovery V0.1

**Status:** `RESEARCH_ONLY / DATA_ONLY / NO_TRUST_ACTIVATION / NO_PRODUCTION`

`ConsolidationEngine.to_snapshot()` produces canonical UTF-8 JSON (`ario.cognitive-memory`, schema version 1). `ConsolidationEngine.from_snapshot()` and `restore_snapshot()` require the caller to supply the retained SHA-256 reference. `core.memory_snapshot.write_snapshot()` writes through a same-directory temporary file, flushes and fsyncs it, then uses atomic replacement; directory fsync is attempted where supported. `restore_snapshot_file()` reads a bounded regular file and still requires that external reference.

The format contains only explicit scalar/list/object data: engine settings, semantic nodes, causal links, ingested event identities, and both replay digest indexes. Derived legacy-ID aliases are rebuilt from validated nodes; no alias cache is trusted. The parser caps bytes, structure depth/markers, record counts and field lengths; rejects duplicate keys, noncanonical JSON, invalid types/numbers, unknown schema versions, invalid references and hash/index inconsistencies; and does not invoke pickle, `eval`, dynamic imports, or data-selected object construction. Recovery constructs and validates an independent candidate before replacing engine state. A failed validation leaves the existing engine unchanged. `ACCEPTED` and `SUPPORTED` node/default admission labels are refused, not rewritten.

This is a byte-integrity and local state-recovery mechanism only. A matching SHA-256 shows that the supplied bytes match the caller's reference; it does **not** establish source authenticity, authorization, freshness, independent custody, semantic truth, or execution provenance. The expected digest must be retained independently; reading a snapshot and computing its own expected digest is not verification. The safe API never auto-loads legacy pickle files. Existing pickle compatibility methods remain for compatibility and are not safe for untrusted input.

Atomic replacement and fsync durability depend on filesystem/operating-system behavior. A crash before replacement leaves the previous target intact (a temporary file may remain); after replacement the target is the complete new file. Windows and filesystems without directory fsync provide weaker post-crash durability. This mechanism does not protect against concurrent hostile filesystem manipulation.

## Joint memory and source-history recovery

`core.memory_snapshot.write_cognitive_memory_snapshot(engine, guard, path)` writes the engine and `SourceMonitoringGuard` history in one bounded canonical JSON document (`ario.cognitive-memory-source-history`, schema version 1), using the same retained SHA-256, JSON budget, and atomic file writer as the engine-only API. `restore_cognitive_memory_snapshot()` validates both independent candidates before taking both state locks and installing either. The guard serializes each attribution's complete revision sequence; recovery validates immutable identity/provenance, revision transitions, references, and cycles, then rebuilds the current attribution index from each validated final revision. A failed decode or validation changes neither target object.

The caller's tool allowlist is not serialized and is preserved exactly on restore. Historical `VERIFIED_EMPIRICAL` entries remain available through attribution history, but recovered entries have no active verification authority: verified-only working-memory retrieval and promotions require evidence recorded in the current process. New empirical observations still use the caller's allowlist. This is not an authenticity claim: the retained digest binds bytes only, and a structurally valid snapshot can still contain false assertions. No Pickle is deserialized.

## Boundary correction

The writer runs the same canonical byte parser and structural limits as the reader before returning or replacing a file. Same-thread engine restore is rejected during batch materialization or active application; existing thread-local state is retained across successful swaps. Joint recovery acquires both object locks in a stable order for capture and installation. Recovery is a deliberate replacement, not a cross-process freshness guarantee. A filesystem error after atomic replace (e.g. directory fsync) can leave the new file present with durability uncertain; only pre-replace failure preserves the prior file unconditionally.
