# Review of Ario R2a-0 Execution Kit v0.1 (2026-11-17)

Reviewer: Claude (AI). Scope: static reading of `r2a0.py`, `RUNBOOK.md`, `tests/test_r2a0.py`, plus probes I wrote and ran locally (CPython 3.13.18). **No live GitHub call was made.** `RESEARCH_ONLY / LIVE_R2A0_NOT_RUN / P0_HOLD`.
Tags: **VERIFIED** (reproduced by running code), **READ** (from reading code, not run), **SUSPECTED** (depends on GitHub behavior I could not check here).

Baseline: the 35 offline tests pass (35/35, as claimed). They are mock-only and none of them covers the findings below.

## Findings (most severe first)

| # | Tag | Where | Defect | Fix |
|---|---|---|---|---|
| K1 | VERIFIED | `parse_gh_response`, line 144 | `parse_gh_response(b"", 1, "PUT")` raises `IndexError` (`"".split("\n\n")[0].splitlines()[0]`). Empty stdout is what `gh` produces on a network failure or auth error. `main()` catches only `ValueError/PermissionError/OSError/RuntimeError`, so on `attempt-merge --execute` the PUT may already have been sent, the exception escapes, and **no journal record of the ambiguous merge is written**. | Treat empty/whitespace output as `HTTP_STATUS_MISSING` with `_unknown_outcome` true for writes; write an **intent** record before the PUT and an outcome record after; catch broadly in `main()` and journal the failure. |
| K2 | VERIFIED | `EvidenceJournal.read/append` | A torn last line (crash mid-write) makes `read()` and every later `append()` raise "Journal corrupt". The receiver then answers 503 to every webhook for the rest of the run, with no recovery procedure. Fail-closed is right, but a live experiment would silently stop collecting. | Define recovery: if only the final line is unterminated/invalid, move it aside, append a RECOVERY record, continue; any other corruption stays HOLD. Add a test. |
| K3 | VERIFIED | `append` + `write_once` | Crash between writing the payload object and the index line leaves an orphan object. GitHub redelivers the same bytes, which hash to the same name, so `open(..., "xb")` raises `FileExistsError` forever (503 loop). The existing test `test_corrupted_orphan_payload_blocks_reuse_of_seq` encodes this as intended. `verify` does not report orphans (reproduced: 1 record, 2 objects, verify passes). | On `FileExistsError`, check that the existing bytes hash to the expected value and continue; have `verify` list unreferenced objects as findings. |
| K4 | VERIFIED | `EvidenceJournal.lock` | The lock is a `threading.Lock`, in-process only. The runbook has the operator run `listen` and `snapshot`/`record` against the same `evidence` directory at the same time. Two processes appending concurrently produced `Journal corrupt at line 2: hash/sequence mismatch` (reproduced with two processes x 40 appends). The README admits "no cross-process locking", but the runbook's own procedure triggers it. | OS-level file lock (e.g. `fcntl.flock`, or `msvcrt.locking` on Windows) around read+append, or one journal directory per process and merge later. State this in the runbook. |
| K5 | VERIFIED | `make_server` | `HTTPServer` is single-threaded and handlers have no timeout. One stalled connection (partial request line) blocked a valid signed webhook for the full 4 s test window; 0 records written. A slow or hostile client in front of the tunnel can cause lost deliveries. | `timeout = 5` on the handler class and `ThreadingHTTPServer` (the journal already serializes appends once K4 is fixed). |
| K6 | SUSPECTED | `snapshot`, `effective_rules`; RUNBOOK preflight | `GET /rules/branches/{branch}` returns rules from **rulesets**. If the lab branch is protected by classic branch protection it returns `[]`, which the tool records as a successful, "complete" read. The runbook also names `required_pull_request_reviews` and `required_conversation_resolution`, which are classic branch-protection names; ruleset rule types differ (`required_status_checks` entries have `context` and `integration_id`; review-thread resolution is a parameter of the `pull_request` rule). | Also collect `GET /repos/.../branches/{b}/protection` and `GET .../rulesets` plus each ruleset's detail (includes `bypass_actors`). Treat an empty rules list as UNKNOWN unless a ruleset is known to apply. Confirm names against live output. |
| K7 | SUSPECTED | `gh_api`, `authorized_merge` | The merge PUT uses whatever `gh` is logged in as, probably the repository owner. If that actor can bypass the ruleset or branch protection (admin, `enforce_admins` off), an accepted merge in Sc1 says nothing about native enforcement: it may be a bypass. The kit records neither the actor nor bypass ability. This can create a **false FAIL** in Sc1/Sc2/Sn. | Record `GET /user` with each snapshot and merge attempt; record ruleset bypass actors; run merges as a non-bypass lab account, or mark results from a bypass-capable actor UNKNOWN. |
| K8 | READ | `parse_gh_response`, `authorized_merge`, runbook | A 405 is recorded as "known rejection" without classification. 405 on the merge endpoint also arises for a disallowed merge method (`merge_method` is hard-coded to `squash`), a merge conflict, or an out-of-date branch. A 405 for the wrong reason would be read as "required check enforced". | Make the runbook classify by `_message` (e.g. "Required status check ... is expected", "Changes have been requested") and treat unmatched messages as UNKNOWN; read the repo's allowed merge methods and choose accordingly. |
| K9 | READ | constants, `snapshot` | `APP_ID` and `CHECK_NAME` (lines 27-28) are never used. Nothing checks that a check run's `app.id` is 5747504, its `name`, or its `head_sha`; required-check source matching is entirely manual. That is defensible (no derived PASS), but the task asked specifically for this. | Add a read-only "derive" step: for each required `(context, integration_id)` list the matching check runs by `(name, app.id, head_sha)` in creation order with conclusions, flag duplicates and wrong-app same-name runs, and never output "satisfied". |
| K10 | READ | `parse_gh_response`, `snapshot` | Response headers are dropped, so the GitHub `Date` and request-id are lost; Sn (TOCTOU window) needs a GitHub-side time reference and clock-skew estimate. `commits/{sha}/status` is one unpaged call. | Keep only `Date` and `X-GitHub-Request-Id`; page the combined status or compare `total_count` to the list length. |
| K11 | READ | `EvidenceJournal` | Minor: the first creation of `journal.jsonl` and the evidence root are not directory-synced (only `objects/`); each append re-reads and re-hashes every payload (O(n^2)); a non-JSON 2xx body on a PUT is marked `_unknown_outcome: False` although the write probably happened (the merge path still sets `reconciliation_required`). | Directory fsync after creating the index; cache the chain head under the lock; set unknown for any non-parsable 2xx write. |
